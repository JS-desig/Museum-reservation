### 13. 并发/竞态压测(6)

并发回归发现的两处**真实缺陷**(已修复, 见 `app/routers/gate.py`):

1. **同序号指令并发 → HTTP 500**: 幂等设计为「先查后插」, 并发下多个事务同时读到"无记录"再各自插入, 撞 `uk_device_seq` 唯一键抛 `IntegrityError`, 闸机拿到 500 而非首次结果。修复: 取到游客行锁后用 `FOR UPDATE` 复查幂等键(当前读, 可见并发事务刚提交的记录), 并兜住唯一键冲突。
2. **游客选择竞态 → 重复计数/漏核销**: 选人查询未加锁, 并发事务同时选中同一未核销游客; 实测单人并发 5 次 → **5 次成功放行**(应为1次), 三人并发 → 有人重复计数、有人漏核销。修复: 选人查询加 `FOR UPDATE`, 后续事务排队并在锁后重新求值跳过已核销游客。

## 三、闸机异常场景专项(需求3.3测试重点)

### 场景A: 断网重连
```
步骤:
1. 闸机切换离线模式
2. 连续核销5笔(有效2笔/无效1笔/重复1笔/黑名单1笔) → 本地暂存
3. 恢复网络, 打开离线队列 → 显示5条
4. 点击补传
预期:
- 有效2笔: result=success, access_log按pass_time落库
- 无效/重复/黑名单: result=fail, 不产生通行日志
- 重复补传: 全部duplicate=true, 记录数不变
- 后台对账: SQL校验脚本全部PASS
```

### 场景B: 指令延迟
```
步骤:
1. 09:00过闸成功, 但核销指令因网络延迟10:30才到达服务器
2. 补传payload带pass_time=09:00
预期:
- access_log.pass_time = 09:00 (实际过闸时间)
- reservation.checked_in_at = 09:00
- 客流统计按时段分布归入09:00时段
```

### 场景C: 重复核销
```
步骤:
1. 有效票扫码入闸 → success开闸
2. 3秒内同票再次扫码(同seq) → 幂等返回首次success(闸机不重复开闸)
3. 换一台闸机(不同seq)同票刷 → fail 60002 红灯
4. 出馆后同票再刷入馆 → fail(无可用游客)
5. 后台无重复通行记录(SQL校验CON-007)
```

### 场景D: 人已过闸但后台未记录(历史缺陷回归)
```
根因: 核销成功但access_log写入失败/事务未提交
防御: check_record + access_log + 状态更新同事务
回归: CON-002 每日SQL对账 = 0异常
```
